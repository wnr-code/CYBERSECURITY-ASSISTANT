# Market: three priority providers

## Scope and actual capability

Market is organized as three internal sections—Providers, Packages, and AI Models—without changing the app's bottom navigation. The Providers section keeps the three priority providers at the top and links each to a dedicated detail screen; the existing data-package catalog remains in Packages, and Local AI metadata is separated into AI Models. Edge Panel shows only the verified Cloudflare dashboard shortcut and verified Gemini details shortcut; it does not expose service operations whose permissions are unknown. This does not replace or execute package payloads. Credentials use the existing `SecureCredentialStore` on Android secure storage, and a single `MarketProviderManager` owns Market configuration and tests. Gemini's connection check delegates to the existing `AiProviderManager` and `GeminiAiProviderAdapter`; no second Gemini adapter was created. Assistant requests still pass through the existing per-request data-sharing prompt, policy checks, tool review, and bounded runtime bridge.

The three primary Market provider categories are Cloudflare (cloud infrastructure), Gemini (cloud AI), and Local AI (intended offline, on-device AI). For Local AI, Google AI Edge/LiteRT-LM is the recommended Android runtime foundation; Hugging Face and Kaggle are model discovery/catalog references only. The app currently has no catalog integration, model download/import, installation/removal, or runtime inference, so Local AI stays `Not Ready` and all three sources must not be presented as connected providers or working download options.

`Connected` is not persisted across app starts. A saved credential returns to `Disconnected` until the user runs a new successful test. This avoids presenting stale test results as current. These provider adapters are bundled with the app, so they cannot be uninstalled independently; Disconnect explicitly removes only that provider's saved credential/configuration. Other providers and package settings are not deleted. Existing Cloudflare Workers/D1/R2 entries and their older namespaced credentials are left untouched and are not auto-imported because their scope/permissions cannot be inferred safely.

## Market install/uninstall and purpose audit

- **Cloudflare and Gemini provider entries:** bundled application adapters; they are not individually installed or uninstalled through Market. Configure and test them in their detail screens. Disconnect is the supported credential-removal action and requires user confirmation. Cloudflare supports token verification plus read-only account/zone listing and zone details; Gemini uses the existing model-access test and Assistant approval flow.
- **Local AI:** no runtime or model artifact exists in this build. Install, uninstall, model storage, and inference remain unavailable; the detail screen keeps these actions disabled and reports `Not Ready`.
- **Bundled security tools:** compiled into the app and represented by core catalog metadata; they cannot be uninstalled individually. Their actual runs are available through the existing Tools/Runtime path, not by loading package code.
- **Knowledge/evidence guide:** the verified JSON data package can be installed, opened as read-only text after a fresh checksum/schema check, and uninstalled. Opening it never executes package content.
- **Runtime and plugin entries:** unsupported/planned metadata; no binary or plugin installation is offered.
- **AI model and cloud connector entries:** catalog/guide metadata only. They have no usable artifact or adapter, so install is disabled; they do not claim model execution or authenticated cloud integration.
- Installed data packages remain uninstallable even if their current catalog entry becomes incompatible. Packages whose catalog metadata disappears remain listed in an orphaned-installed section so users can still remove app-managed data.

## Permissions and safety

- **Cloudflare:** This build calls token verification, `GET /accounts`, `GET /zones`, and `GET /zones/{zone_id}` only. Cloudflare's API reference lists `Zone Zone Read` as the accepted minimum permission for zone listing; endpoint responses—not token verification—determine access for each implemented read. No DNS record, Workers, D1, R2, Pages, Security, Analytics, or write endpoint is called. A broad token's full privileges are not enumerated; use a dedicated, short-lived token scoped to only account visibility and `Zone Zone Read` for the account/zone reads you intend to use. Do not grant `Zone DNS Read` for this feature because DNS records are not requested.
- **Gemini:** The key is user's own and is sent in the `x-goog-api-key` header to Google's fixed API origin. Saving the key makes no request; Test Connection sends the key but no prompt. Google's documentation warns client-side/mobile keys can be extracted and abused. Android secure storage reduces casual disclosure, not extraction by a device owner or compromised OS. Don't put production service keys in a distributed client; users must understand billing and key-abuse exposure.
- **Gemini data:** Each Assistant send retains the existing explicit data-sharing confirmation before sending the prompt and any subsequently approved tool results. The confirmation is not bypassed by Market. Google distinguishes paid and unpaid services: unpaid-service prompts/responses may be used to improve products and may be reviewed by humans; paid-service prompts are not used for product improvement but may be logged for safety/legal reasons. Do not submit sensitive, confidential, or personal data. Google's current API terms describe Gemini API/AI Studio as developer services for professional or business use rather than consumer use; users must confirm their use case and region comply. Pricing and quota can change; the UI points to the current official pricing page rather than hard-coding estimates.
- **Local AI:** Device-resource telemetry is read through Android's built-in APIs and does not request filesystem workspace access or network permission. Google AI Edge/LiteRT-LM is the prioritized future Android runtime. Hugging Face and Kaggle are catalog references only; they are not queried by the app. No runtime/model is present, no inference is claimed, no model file is downloaded, and no cloud service is used as fallback. Before a future import/download implementation, verify each artifact's exact model format/runtime compatibility, publisher identity, license/usage restrictions, integrity hash, storage size, and any required network or storage consent.
- **Policy/runtime:** Provider credentials are not passed into Market packages. Gemini tool proposals remain untrusted until they pass the existing user review, `PolicyEngine`, and runtime authorization. No provider receives direct workspace filesystem access. Cloudflare operations in this phase are limited to the explicitly listed read-only account/zone GET endpoints; write methods are not exposed.

## Cloudflare Integration 1 — Account & Zone Read-Only

- The dashboard reads actual account name/type from `GET /accounts`, paginated zones from `GET /zones` (optionally filtered by the locally saved Account ID), and actual zone details from `GET /zones/{zone_id}`. Zone listing uses only `Zone Zone Read`; no DNS-record or write endpoint is requested.
- Cloudflare's `GET /user/tokens/verify` returns token status and dates, not permission scopes. Therefore the app marks account/zone capabilities `Allowed`, `Denied`, `Error`, or `Not checked` only from the respective read endpoint result. A permission denial leaves the token's prior connection status separate from the denied capability; the UI never treats it as permission for that action.
- API calls use fixed-origin HTTPS GET requests with an endpoint allowlist, redirect disabled, bounded timeouts and response sizes, bounded pagination, and credential-free errors. Only selected account/zone fields are rendered; activity summaries contain the operation label and fixed API host, not account IDs, domain names, nameservers, or token values. Each read is persisted to the existing app Activity Timeline.
- The implementation has fake-transport manager tests for token gating, allowed list/detail responses, permission denial, query scoping, no-secret activity records, and API-only read boundaries. These Flutter tests remain unrun until Flutter/Dart are available. Build and device testing are still required.

## Implementation notes and validation

- Android Kotlin and Java scaffold templates wire an Android-only capability channel. They only report device resources; the channel does not execute a runtime or open files selected by the user.
- Local model documentation lists Gemma 4 E2B/E4B mobile inference memory estimates; the UI calls these candidates, not compatible/downloadable models. Required RAM varies by quantization/runtime and the exact artifact disk size must be checked with its publisher before any future download workflow.
- The Gemini endpoint was minimally moved from the existing 2.5 Flash model to `gemini-3.5-flash-lite`: current official model documentation marks `gemini-2.5-flash` deprecated/restricted and recommends a newer model. The existing adapter, consent flow, and tool-policy path were retained.
- Python configurator/source tests cover Kotlin/Java native channel generation and idempotence. Dart manager/widget tests were added but remain **NOT RUN** unless Flutter/Dart are installed. Android native code has not been compiled on a generated scaffold or tested on a device in this workspace. Therefore this documents implemented source behavior and available tests, not an APK/device verification claim.

## Local AI Foundation: implementation gates

The user-approved provider split remains unchanged: Cloudflare (infrastructure), Gemini (cloud AI), and Local AI (intended offline, on-device AI). Do not add another AI provider.

### Runtime integration decision

Google's official LiteRT-LM repository documents a **stable Kotlin API for Android** and lists Flutter support as **community** support. Its Android API accepts a `.litertlm` model bundle through `EngineConfig(modelPath: ...)`; engine initialization can take several seconds and must run off the UI thread, and Engine/Conversation resources must be closed. Therefore the production integration should use the native Android Kotlin API behind a narrow Flutter platform-channel adapter, rather than creating a second Flutter-side inference engine. Do not resolve `latest.release` in production; pin a tested Maven version after inspecting the generated Android Gradle/Kotlin toolchain and validating dependency resolution.

Source reviewed: [LiteRT-LM Kotlin API getting started](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md) and [official LiteRT-LM repository README](https://github.com/google-ai-edge/LiteRT-LM). These GitHub sources identify the Android artifact/API, `.litertlm` input path, lifecycle requirements, and platform support levels. The app currently has no generated `android/` scaffold, and Flutter/Dart/Gradle/Java SDK commands are unavailable in this workspace, so adding an unbuildable Gradle dependency or claiming runtime integration would be unsafe. Runtime code remains a blocked next implementation stage until a generated scaffold and build toolchain are available.

### Required staged gates

1. **Native runtime bridge:** pin a compatible Android Maven artifact and Kotlin toolchain; expose only initialize, inference, cancellation, and close operations over a versioned platform channel; perform model initialization/inference on background dispatchers; translate failures to bounded non-secret messages.
2. **Compatibility inspection:** `core/local_ai_model_compatibility.dart` now defines a pure, fail-closed policy contract for verified metadata/runtime/device profiles. Its unit tests cover exact bundle format, architecture/model family, tokenizer, minimum runtime version, ABI intersection, peak memory with headroom, install storage, publisher metadata, and artifact digest. It is not yet connected to a file inspector or native runtime, and its Dart tests have not been run. Production eligibility still requires trusted metadata/runtime inspection for all these fields. Unknown/missing metadata is `Unknown`, never compatible by extension, RAM, or ABI alone. A hash proves file integrity against a trusted manifest, not publisher identity by itself.
3. **Model Manager:** only after the runtime's supported bundle contract and publisher metadata are verified. Use app-private no-backup storage rather than the workspace filesystem; require explicit download consent; enforce source/redirect/size/time limits; verify a trusted digest/signature before atomic install; prevent path traversal; preserve license/attribution; and only delete models managed by this manager. Hugging Face and Kaggle remain catalog references until a safe, specific artifact source is reviewed.
4. **Offline inference gate:** Test Inference must load the installed model and complete a bounded local prompt successfully before Market can report `Ready`. Add an instrumented test with network blocked/denied during inference and verify that no Gemini/Cloudflare request or fallback occurs. On failure, remain `Not Ready` and cleanly release runtime resources.
5. **Assistant integration:** register one `LocalAiProviderAdapter` only when that runtime/model readiness contract passes. Keep the existing Assistant consent and request boundaries; treat model output/tool calls as untrusted and route every proposed tool through the existing `AiTerminalExecutionBridge`, user review, Policy Engine, and runtime authorization. Never expose a shell or workspace path to model code.
6. **Release validation:** run Flutter analysis/unit tests, generated Android debug/release builds, dependency/license review, and physical-device tests across supported Android API/ABI combinations. Record model ID, artifact digest, runtime version, device/backend, cold-start, memory, storage, and inference results without logging prompts or secrets.

These are acceptance gates, not claims that any gate is already implemented. Local AI continues to report `Not Ready` until the runtime is loaded, the installed model passes compatibility checks, and an actual on-device inference succeeds.
